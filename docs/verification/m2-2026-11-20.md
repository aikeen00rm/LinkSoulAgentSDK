## Limitations and recovery

Hardware acceptance remains Pending. Required dependencies: isolated ASR-text agent configuration/physical association, robot credentials and gateway, firmware/developer entitlement, and a running Ollama model reachable from the application. Real callbacks, provider output, history publication, three real input/replies across recreation and physical playback have not been observed. The pinned SDK may swallow send errors; call return means attempted sending only. No acknowledgement/playback is claimed.

Retention is bounded and visible: default 100 sessions/mode, 200 turns/session, 8,192 characters/text event, fixed 4,000 events/session, 128 MiB SQLite page cap. Capture/write failures invalidate verification. History arriving after a reconnect stays unassigned when it cannot be linked uniquely within the current session; it never attaches by timing.

The stopped pre-upgrade volume copy succeeded. Full restore into a separate clean volume remains unperformed. Keep the previous image and complete volume backup for rollback; older releases are not declared schema-compatible. Ordinary recreation preserves M1 and M2 data. Never use `down -v` for an update.

Next action: configure/confirm the isolated ASR-text callback and live provider, complete M1 hardware verification, then use the explicit M2 reply connection for three short robot interactions and verify their persistence after recreation. M3 can build on the fixture-ready store while these hardware gates remain pending.
